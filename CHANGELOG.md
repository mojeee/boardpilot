- Pico SDK starter projects (issue #11, part 1): on RP2040 and RP2350 boards, New project can write a Pico SDK project instead of an Arduino sketch (pick "Pico SDK", then "Save project folder…"; it never overwrites a file). The project uses only the pins in your drawing and starts I2C, SPI, the ADC and PWM where the chip allows it. It reads each part's chip ID when the parts library has one, and gives every hardware fact its datasheet source. Wiring it cannot use, like a pin pair that is not I2C, is explained in plain words. A nightly job builds every template on the Pico, Pico 2 and Pico W with the real SDK; the first 15 projects were compiled to .uf2 here. ESP-IDF and STM32 HAL come next.
- Schematic view (issue #5, completes it): the Diagram tab switches between Wiring and Schematic. The schematic shows the board with only the pins in use, standard symbols for LEDs, buttons, switches and potentiometers, boxes with pin names for modules, and power and ground symbols instead of long wires. Wires that would cross become net labels such as SDA and SCL, and wiring warnings sit on the pin or wire they are about. Pull-ups, dividers and level shifters the rules ask for are drawn dashed as "suggested, not in your drawing". It saves as SVG, is in the report next to the wiring diagram, and is tested for overlaps on every template on every board.
- State machine designer (issue #12, New project): draw states, events and transitions with an optional condition and action, and see the machine as a diagram in the lesson style. Plain-language checks flag unreachable states, states with no way out, unhandled events and duplicate transitions. The app writes C code (enums, a switch-based `handle_event`, a transition table and hook stubs), a host unit test that walks every transition, and an Arduino sketch; the tests compile the generated C with `-Wall -Werror`. It starts from four examples (thermostat, traffic light, button debounce, Plant watering), and the machine is saved with the project.
- Guided portfolio projects (issue #16, New project → "Portfolio project, stage by stage"): the Smart room monitor is built in 8 stages: blink, serial hello, button, knob, BME280, OLED, the whole project, and FreeRTOS tasks on ESP32. Each stage shows hints first, then finished reference code for your board and wiring on request. Each stage is checked on the board: the lesson labs for GPIO, ADC and I2C, a bus scan for the display, and your sketch's serial output for the others. "Export for GitHub" saves a README with each stage and how it was checked, the wiring diagram, a pin table, the shopping list and a photo placeholder, plus the finished sketch. It also comes as a new template, and the simulator has its bench, so the whole project runs end to end without hardware (tested). Two more projects use the same format, with 7 stages each. The Industrial sensor node has a DS18B20 probe, a fan relay and a latched alarm. The Predictive-maintenance device has an MPU6050 read through its registers, vibration RMS, a learned baseline and a fault LED and buzzer. Both are also new templates, and all three pass the wiring and code checks on every board.
- Timing view in Monitor (issue #8): one row per streamed pin, coloured by its role, with the agent's decoded I2C transaction drawn under SDA/SCL (labelled "agent trace, not sampled"). It is honest about being sampled: it shows the measured sample rate, draws each edge across the time between two samples, and says that shorter pulses can be missed. Two cursors measure time, and a selected row shows its period, frequency and duty cycle with their uncertainty, or says "not enough edges" instead of guessing. Pause, zoom, and export to PNG and CSV. In the simulator, PWM now follows its real phase, so slow PWM draws a proper square wave.
- Interview coach (issue #17): every interview question in a lesson has a "Practise" button. Type your answer and the assistant says what was right, what is missing and one follow-up a senior interviewer would ask. The feedback is labelled as a suggestion and cites the lesson section it used. It works with the free demo and with your own key, and shows the lesson's key points when the assistant is not available. Your answers stay on this computer, are deleted after 90 days, and can be deleted per question or all at once.
- A YouTube channel plan (issue #23) in `docs/youtube/`: research on 10 embedded channels, with what was checked and what still needs checking; the channel format; a low-budget voice-and-hands recording setup; an 8-week calendar; Italian subtitles that use the app's own words; the first 6 videos and 4 Shorts ready to record, each claim tied to a file in the repo. - Register maps, decoded live (issue #14): the BME280, MPU6050 and SSD1306 show their datasheet register table, and the app reads the real values from the board and explains every bit ("ctrl_meas = 0x27 → temperature ×1, pressure ×1, normal mode"; "PWR_MGMT_1: the sensor is asleep, your code must clear bit 6"). Open it from the part card or in Test hardware. It only reads, never writes, and skips registers where a read would clear flags or data. Every register cites its datasheet section; values the datasheet does not describe are shown as undocumented, never guessed. The SSD1306 is mostly write-only, so only its status byte is read and the command table is marked "documented, not read from the chip". Works in the simulator, with a new "Motion sensor reads zeros" bench; the decoder is tested with worked datasheet values.
- Hands-on labs in the lessons (issue #7): Blink (GPIO lesson), Button (GPIO), Knob (ADC) and I2C sensor (buses) end with a lab that the app checks with live data, on any board with the diagnostic agent or in the simulator. Each lab finds the part in your project (it asks for the pin only when it is not there) and installs the agent after a confirmation and backup. It then measures: the LED pin read back after each write, a steady 1 released and 0 pressed with the pull-up checked, the knob covering at least 70% of the ADC range, and the scan plus chip-ID read with the swap test. One confirmation covers the blink's 6 writes and says so. When a lab fails it says why in plain words, from the measurements: input-only pin, floating button, loose knob leg, crossed SDA/SCL. A passed lab marks its lesson done, and every result is in the session log and the report. The simulator gets "press the button" and "turn the knob" buttons in the lab steps and a new "three beginner mistakes" bench; 9 new flow tests cover success and failure for every lab.
- Calculators for timers, PWM, UART and ADC (issue #10, New project → "Calculators"). They use the board's real clocks, from a new sourced `clocks` section in all 13 board files. Timer/PWM gives the prescaler, period and compare values, the real frequency and the duty steps. UART gives the divider, the real rate and whether the error is fine, borderline or too much ("16 MHz cannot make exactly 115200 baud: nearest is 117647, 2.12% error, which is too much"). ADC gives the fastest reading rate for each setting. Code is ready to paste for the board's toolchain: AVR registers, STM32 HardwareTimer / HAL / registers, ESP32 `ledcAttach` and ESP-IDF, Pico SDK, Adafruit nRF52. Tested against the datasheets' own examples (ATmega328P UBRR table, RM0368 baud table, Espressif's 5 kHz / 13-bit LEDC example). Where a figure is not published (ESP32 analogRead time, Teensy timers), it says so instead of guessing.
- Power budget and battery life (issue #13, in New project and Report): the board and every part with its datasheet current (awake, asleep, peak) and source, the time awake, how often it wakes up and the battery size you choose, then the average current, the peak with everything on, the battery life and which devices use the most. Currents come only from datasheets: 13 parts and the ESP32 DevKit and Pico boards have a sourced `current` / `power` field (checked by the board and part validators); a part without one is listed as unknown and left out, never guessed. Labelled as an estimate, not a measurement.
- Lessons can show their example on the 3D board (issue #6). A "Show on the 3D board" button opens a split view with the board, parts and wires and the pins highlighted, in five lessons (a NUCLEO-F401RE's PA5, an LED and a button on an ESP32, an interrupt button on a Pico, an I2C sensor on the ESP32's default bus, an LED resistor on a Pico). Your project is set aside and comes back exactly as it was, including undo history and view; nothing is autosaved and the hardware board is not switched while a preview is open (tested).
- BoardPilot as an MCP server (issue #21): AI coding agents (Claude Code, Cursor, Claude Desktop) can use the real board through BoardPilot. The server offers 18 tools: identify, board and part data, the project, wiring and code checks, live pins, I2C scans with traces, ADC, serial output and the log. Board and part files are available as resources. Every result carries its provenance (measured or documented, source, time, board). Writes only ask: the app shows its usual confirmation dialog, and nothing is written without the click. Localhost only, with a per-session token, and off by default (AI settings → AI agents). `BoardPilot --mcp-stdio` bridges a client to the running app; with the app closed it runs without a window and refuses every write. Every call appears in the session log as "MCP: <client>". Setup in `docs/mcp.md`. New dependency: `@modelcontextprotocol/sdk` (approved).
- New lesson "Hardware basics for software developers" (issue #15), second in Foundations: voltage, current and resistance, Ohm's law, LED resistors, pull-ups, voltage dividers, 5 V vs 3.3 V and level shifting, reading a schematic and a datasheet's first page, with tips and interview questions. It has three interactive calculators: LED resistor (E12 value to buy, real current, heat), voltage divider (output, current, R2 for 3.3 V), and I2C pull-up (allowed range and rise time from the NXP I2C specification, per bus speed). The calculators are tested against worked examples, and every text is in Italian too.
- Pin planner (issue #9, New project → "Plan my pins"): say what the project needs (I2C, SPI devices, serial ports, analog inputs, PWM, digital outputs and inputs, Wi-Fi on or off) and the app picks pins from the board file only, with the reason for each. It uses the default buses, a hardware UART that is not the USB one, ADC1 when Wi-Fi is on, PWM-capable pins and safe pins, and leaves pins already wired alone. When something does not fit, it says what to do (software serial, an ADS1115). "Show on the board" highlights the pins in 3D, "Copy #defines" gives the code names, and "Save pin map" writes a Markdown table. Tested on all 13 boards.
- Shopping list (issue #18): the board and its USB data cable, the parts grouped with quantities, jumper wires and a breadboard, plus the extras the wiring rules imply, each with its reason. Extras cover I2C pull-ups when no part has them, 1-Wire pull-ups the part notes ask for, a 1 kΩ + 2 kΩ divider for each 5 V output into a 3.3 V pin, and level shifters for two-way lines. Shown in New project and in Report, saved as CSV or Markdown, and included in the exported report.
- Wiring diagram (issue #5, wiring view): a "Diagram" tab next to 3D and 2D pinout draws the project flat. The board shows the pins in use in their real header order, with a mark where pins are skipped; parts show their pins; each wire runs in its own lane, so none overlap. Wiring findings sit on the pin or wire they are about, and clicking anything selects it as in 3D. Saves as SVG, and the report (Markdown and PDF) now includes the diagram. The layout is a pure, tested function (every template on every board). The schematic view comes next.
- Template projects (New project → "Start from a template"): Blink and button, Weather station (BME280 + OLED), Distance meter (HC-SR04 + TM1637), Motion alarm (PIR + buzzer + LED) and Plant watering (soil sensor + relay). Each one builds itself on the selected board: parts in front of it, wires from the board's own pin rules, and Arduino code written for that board's core. Every template on every board passes the wiring checker and the code checker (tested).
- Live run view in the simulator: Run, Pause, One step and 1×/2×/4× speed. The program's story appears in plain words (steps, mode, events, pin changes, readings), and each line can be clicked to focus its pin or part. The running step is highlighted in the code. In 3D, pins light up, LEDs glow, wires pulse on bus reads, and parts show their latest value or display text. Everything is labelled simulated and kept apart from measured data.
- BoardPilotProbe 0.2: `probe.step()`, `probe.state()` and `probe.event()` story markers (step and state only send when they change), and the library now builds on every board (the memory line stays ESP32 only). The app reads the markers from serial.
- STM32 pin names: boards whose pin ids are already chip names (Black Pill: PB10) now get `PB10` in generated code instead of an internal number.
- Part "gotchas": 44 known traps for the 27 most used parts, each with its datasheet source (DHT22 needs 2 s between reads, HC-SR04 ECHO is 5 V on a 3.3 V board, SSD1306 at 0x3C or 0x3D and "0x78" printed on the board, WS2812 power and data level, DS18B20 pull-up and 750 ms conversion, servo supply, SD cards must be FAT32…). They appear in the log the moment the part is added and on the part's card. Board-specific ones show only where they apply (3.3 V boards, Uno/Nano/Mega). User parts keep them too (new optional `gotchas` field). The website shows them on part pages and on each wiring guide, in English and Italian.
- Flash pre-flight check: before anything is written, Flash firmware reads the file and checks that it is made for the board. Covered: the format the board takes; the ESP32 image header (chip, flash size, app size against the default partition, merged images); the UF2 family (RP2040 vs RP2350); Intel HEX checksums and size (with a warning near the AVR bootloader, and nRF52 UICR records left out); the STM32 vector table (stack in SRAM, start in flash). A problem stops the flow with the reason and "Choose another file"; warnings are shown before the confirmation. Every result is read from the file itself.
- Sharper pictures: screenshots are captured at 2x pixel density (README 2400 px, website 1800 and 900 px, matching the sizes the pages declare), and each board's social image now shows the bare board, large and crisp.
- Silkscreen: pin names that would print under a chip or button move to a free side of their pin when there is one.
- Roadmap: a last step for October, an interactive demo of the app on the website (the simulator running in the page, no install), as you asked.
- Code vs wiring checker (New project → "Check my code against the drawing"): open or paste an Arduino sketch and it is compared with the 3D drawing. It catches `Wire.begin(22, 21)` when the drawing has SDA on 21, `pinMode(34, OUTPUT)` on an input-only pin, pull-ups on pins that have none, `analogRead` on a pin with no ADC or on ADC2 while the sketch turns on Wi-Fi, the LED wired to one pin while the code drives another, `Serial.begin` at a different speed than the monitor, flash pins and pins that are not on the header. Findings show the code line, highlight the pin in 3D, go to the session log, and are labelled as checks of the drawing, not measurements. Pin numbers follow each core (GPIO numbers, STM32 names such as PA5, header numbers on STM32 and nRF52, `LED_BUILTIN`, `#define` and `const` pins).
- New wiring rule: two I2C parts on the same bus that answer at the same default address (two BME280s at 0x76, two BH1750s at 0x23). It is a warning when one part can move, and the hint names the address pin from the library ("Set BH1750 to address 0x5C with its ADDR pin"). It is an error when neither part can change its address.
